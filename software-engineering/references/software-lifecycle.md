# 软件生命周期详解

软件从产生到淘汰经历的所有阶段。本文档详解每个阶段的**工作内容、产出物、评审要点**，供软件工程技能在执行开发工作流时参考。

---

## 生命周期总览

```
可行性研究 → 需求分析 → 概要设计 → 详细设计 → 编码实现 → 软件测试 → 软件部署 → 运行与维护
```

> **关键提示：维护阶段通常占整个软件生命周期成本的最大比例**（约 60%-80%），因此在开发时就应考虑可维护性。

---

## 阶段 1：可行性研究（Feasibility Study）

### 目的
在投入大量资源前，评估项目是否值得做、能否做成。

### 评估维度
| 维度 | 内容 |
|------|------|
| 技术可行性 | 现有技术/团队能否实现 |
| 经济可行性 | 成本收益分析、ROI |
| 操作可行性 | 用户能否接受与使用 |
| 法律可行性 | 是否符合法律法规 |
| 进度可行性 | 能否在期限内完成 |

### 产出物
- **可行性研究报告**

### 评审要点
- 风险是否可控
- 收益是否大于成本
- 是否决定立项

---

## 阶段 2：需求分析（Requirement Analysis）

### 目的
明确系统**应该做什么**，是开发的基础。

### 需求分类
- **功能需求**：系统必须提供的功能行为
- **非功能需求**：性能、安全、可用性、可靠性、可维护性、可移植性、合规性
- **约束条件**：技术栈、平台、预算、时间

### 工作内容
1. 需求获取（访谈、问卷、观察、原型）
2. 需求建模（用例图、数据流图、ER图、类图）
3. 需求验证（评审、原型确认、可追踪性检查）

### 产出物
- **软件需求规格说明书（SRS）**，模板见 `../assets/srs-template.md`

### 评审要点
- 需求是否完整、无歧义、可验证
- 是否遗漏关键非功能需求
- 是否可追踪（需求→设计→测试）

---

## 阶段 3：概要设计（Architecture / High-Level Design）

### 目的
定义系统的**整体结构**，不深入到具体实现。

### 工作内容
1. **系统架构**：模块划分、层次结构、技术选型
2. **模块设计**：模块职责、模块间接口
3. **数据库设计**：概念模型（ER图）、逻辑模型
4. **接口设计**：外部接口、内部接口、用户界面框架

### 设计原则
- **抽象**：忽略次要细节，聚焦核心
- **模块化**：划分为独立模块
- **信息隐藏**：内部实现对外隐藏，只提供接口
- **高内聚低耦合**：模块内联系紧密，模块间依赖少

### 产出物
- **概要设计说明书**，模板见 `../assets/design-doc-template.md`

### 评审要点
- 架构是否满足需求（含非功能需求）
- 模块划分是否合理（高内聚低耦合）
- 技术选型是否合适

---

## 阶段 4：详细设计（Detailed Design）

### 目的
将概要设计细化到**可编码实现**的粒度。

### 工作内容
1. 类/数据结构设计
2. 方法/函数设计与算法
3. 数据库表结构设计
4. 接口详细规格
5. 异常与边界处理

### 产出物
- **详细设计说明书**
- 数据结构/类图、时序图、状态图

### 评审要点
- 每个模块是否可独立编码
- 边界条件与异常是否处理
- 是否符合概要设计的约束

---

## 阶段 5：编码实现（Implementation）

### 目的
将详细设计转化为**高质量、可维护的代码**。

### 工作内容
1. 遵循编码规范（命名、缩进、注释）
2. 编写可复用、可测试的代码
3. 配合单元测试（若用 TDD：先写测试再写实现）
4. 持续集成、代码评审（Code Review）

### 质量要点
- **可读性**：清晰命名、合理注释
- **可维护性**：便于修改升级
- **可重用性**：模块复用
- **可扩展性**：方便增加功能

### 产出物
- 源代码、单元测试、构建脚本

### 评审要点
- 是否遵循规范
- 单元测试覆盖是否充分
- 是否有明显坏味道（重复、过长函数等）

---

## 阶段 6：软件测试（Testing）

### 目的
发现缺陷，验证软件**满足需求**且**质量达标**。

### 测试层次
| 层次 | 对象 | 说明 |
|------|------|------|
| 单元测试 | 最小代码单元（函数/类） | 开发阶段进行 |
| 集成测试 | 模块间协作 | 验证接口与集成 |
| 系统测试 | 整个系统 | 验证整体功能与非功能 |
| 验收测试 | 用户视角 | 用户确认是否满足需求 |

### 测试类型（按内部结构了解程度）
- **黑盒测试**：只关注输入/输出，不关心内部实现（等价类划分、边界值分析、因果图、错误推测）
- **白盒测试**：关注代码逻辑与执行路径（语句覆盖、分支覆盖、路径覆盖）
- **灰盒测试**：结合黑盒与白盒

### 详细测试策略见 `testing-maintenance.md`

### 产出物
- **测试计划、测试用例、缺陷报告、测试报告**

### 评审要点
- 覆盖率是否达标
- 是否覆盖边界与异常场景
- 缺陷是否分类与定级

---

## 阶段 7：软件部署（Deployment）

### 目的
将软件发布到目标环境，供用户使用。

### 工作内容
1. 构建与打包（编译、打包、版本标记）
2. 环境配置（服务器、数据库、依赖）
3. 数据迁移
4. 上线发布（蓝绿部署、灰度发布、回滚预案）

### 产出物
- 发布版本、部署文档、运维手册

---

## 阶段 8：运行与维护（Maintenance）

### 目的
保证软件长期稳定运行，并持续满足业务变化。

### 四类维护
| 类型 | 说明 | 示例 |
|------|------|------|
| 纠错性维护 | 修复软件缺陷 | 修复 bug、崩溃 |
| 适应性维护 | 适应环境变化 | 支持新OS、新硬件、新数据库 |
| 完善性维护 | 优化或新增功能 | 性能优化、功能增强 |
| 预防性维护 | 改进结构降低未来成本 | 重构、文档更新、架构优化 |

### 工作内容
- Bug 管理（缺陷跟踪、修复、回归）
- 性能监控与调优
- 版本迭代与升级
- 用户支持

---

## 各阶段评审表（可用于阶段门控）

| 阶段 | 关键评审问题 | 通过标准 |
|------|-------------|---------|
| 可行性 | 值得做吗？能做吗？ | 风险可控、收益明确 |
| 需求 | 完整、清晰、可验证吗？ | SRS 通过评审 |
| 概要设计 | 架构满足需求吗？ | 架构方案通过 |
| 详细设计 | 可编码吗？ | 设计细化完成 |
| 编码 | 质量达标吗？ | 测试通过、无严重缺陷 |
| 测试 | 达到发布标准吗？ | 验收测试通过 |
| 部署 | 稳定上线吗？ | 线上验证通过 |
| 维护 | 运行健康吗？ | SLA 达标 |
