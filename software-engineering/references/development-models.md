# 软件开发模式详解

本文档详解五种主流软件开发模型（瀑布、原型、增量、螺旋、敏捷）的执行细则、适用场景与相互切换策略。使用软件工程技能时，据此决定采用何种模式并按其节奏执行生命周期工作流。

---

## 决策速查表

| 模式 | 触发场景 | 迭代节奏 | 文档要求 | 用户参与度 |
|------|---------|---------|---------|-----------|
| 瀑布 | 需求明确、稳定、变化少 | 无迭代，线性 | 极高（全文档） | 低（阶段评审） |
| 原型 | 需求模糊，需澄清 | 原型迭代 | 中 | 高（反复确认） |
| 增量 | 需分批交付可用功能 | 多次增量 | 中高 | 中 |
| 螺旋 | 大型高风险 | 风险驱动迭代 | 高 | 中（阶段评审） |
| 敏捷 | 需求变化快、快速交付 | 短迭代（Sprint） | 低（工作软件优先） | 极高（持续反馈） |

---

## 瀑布模型（Waterfall）

### 核心思想
按阶段**严格线性顺序**推进，前一阶段完成并评审通过后才进入下一阶段，不可回退。

### 阶段顺序
```
可行性研究 → 需求分析 → 概要设计 → 详细设计 → 编码实现 → 软件测试 → 软件部署 → 运行维护
```

### 执行细则
1. 每一阶段结束后产出**正式文档**并进行**阶段评审**（Review）
2. 评审通过才可进入下一阶段
3. 需求变更需走**变更控制流程**，成本较高

### 适用场景
- 需求明确且很少变化的项目（政府、银行、医疗、基建类）
- 对文档完整性有强制要求的合规项目
- 技术成熟、风险较低的项目

### 优点
- 管理简单，阶段清晰，易于控制
- 文档齐全，利于人员交接与维护

### 缺点
- 难以应对需求变化
- 后期修改成本高，错误发现晚（测试在最后）
- 用户到很晚才能看到可运行软件

### 使用时的角色分工
- 分析师：需求分析、SRS
- 架构师：概要设计
- 开发者：详细设计、编码
- 测试员：测试计划、执行

## 原型模型（Prototype）

### 核心思想
先快速构建一个**可运行的原型**（骨架或部分功能），通过与用户反复沟通来**澄清并确定需求**，原型确认后再进行正式开发。

### 执行流程
```
快速构建原型 → 用户试用反馈 → 修改原型 → 需求确认 → 正式开发
```

### 执行细则
1. 原型是**需求澄清工具**，不是最终成品，需向用户说明
2. 快速迭代修改原型，直至用户认可
3. 需求确认后，可选择丢弃原型重新开发，或基于原型演化

### 适用场景
- 需求不明确、用户难以描述具体需求的项目
- 全新的业务领域或用户体验设计
- 界面和交互为核心的系统

### 优点
- 快速澄清需求，减少返工
- 用户参与度高，满意度好

### 缺点
- 原型可能被用户误认为成品
- 若演化式开发，原型架构可能不稳固

### 使用时的角色分工
- 开发者/设计师：快速构建原型
- 用户：试用并提供反馈
- 分析师：整理需求确认结果

## 增量模型（Incremental）

### 核心思想
将系统按功能拆分为多个**增量（Increment）**，每个增量都提供一部分可用功能，**分批交付**，每次交付一个可运行的版本。

### 执行流程
```
整体架构设计 → 增量1（设计+编码+测试+交付）→ 增量2 → ... → 增量n
```

### 执行细则
1. **先完成整体架构设计**，确保增量可扩展
2. 按**优先级**确定增量顺序，先交付核心/高价值功能
3. 每个增量都是一个完整的小型瀑布（含设计、编码、测试）
4. 用户在每个增量后都能使用部分功能

### 适用场景
- 需要**较早交付可用系统**的项目
- 需求可分阶段、核心功能优先的软件
- 团队资源受限，需分批交付

### 优点
- 用户能较早使用系统，反馈及时
- 风险分散，单点失败影响小
- 交付灵活，可调整优先级

### 缺点
- 需要整体架构设计的前期投入
- 若架构不佳，增量整合困难

### 使用时的角色分工
- 架构师：整体架构与增量规划
- 开发者：各增量实现
- 测试员：每增量回归测试

## 螺旋模型（Spiral）

### 核心思想
**风险驱动**的迭代开发模型。每一轮迭代都是一个四阶段循环，每轮通过原型/风险评估逐步降低风险，每轮结束生成一个**演化原型**。

### 每轮循环四阶段
```
1. 计划（目标、约束、方案）
2. 风险分析（识别风险、评估、制定对策）
3. 开发（构建原型/产品增量）
4. 评审（用户评审、规划下一轮）
```

### 执行细则
1. 每一轮开始前**明确目标与约束**
2. 重点进行**风险识别与评估**，为高风险项制定对策（原型验证、仿真等）
3. 本轮产出经用户评审后进入下一轮，螺旋半径逐渐增大
4. 迭代次数取决于剩余风险与预算

### 适用场景
- **大型、高风险**项目（复杂系统集成、新技术应用）
- 需求不完全明确且风险因素多的项目

### 优点
- 风险在早期被识别和化解
- 迭代可控，结合了原型和瀑布的优点

### 缺点
- 过程复杂，管理成本高
- 对风险评估能力要求高
- 不适合小规模低风险项目

### 使用时的角色分工
- 项目经理：每轮计划与风险分析
- 架构师/技术专家：风险评估
- 开发者：构建演化原型
- 用户/干系人：评审

## 敏捷开发（Agile）

### 核心思想
**小步快跑、快速迭代、持续交付、拥抱变化**。强调团队自组织、用户反馈、可持续的开发节奏，以**可工作的软件**为主要进展衡量标准。

### 常见方法

#### Scrum
- 固定长度的**Sprint**（通常1-4周）
- 角色：Product Owner、Scrum Master、开发团队
- 工件：Product Backlog、Sprint Backlog、增量
- 活动：Sprint 计划会、每日站会、Sprint 评审会、Sprint 回顾会

#### Kanban（看板）
- 可视化工作流，用看板管理任务状态（To Do / Doing / Done）
- 限制在制品（WIP）数量，追求持续流动
- 无固定迭代，按能力持续交付

#### XP（极限编程）
- 强调工程实践：TDD、结对编程、持续集成、简单设计、重构

### 执行节奏（以 Scrum 为例）
```
产品待办列表(Product Backlog) → Sprint 计划会 → 开发(每日站会) → Sprint 评审会 → 回顾会 → 下一Sprint
```

### 执行细则
1. 每次 Sprint 开始时**拆分需求**为可交付的用户故事（User Story）
2. 每日**站会**同步进度、识别阻碍
3. Sprint 结束交付**可运行的增量**并做演示
4. 通过**回顾会**持续改进流程
5. 拥抱需求变化，Backlog 持续调整优先级

### 适用场景
- 需求变化频繁、需快速响应市场的项目
- 用户/客户能持续参与反馈
- 中小团队、跨职能协作

### 优点
- 快速交付价值，响应变化
- 用户满意度高，风险持续可见
- 团队协作与质量意识强

### 缺点
- 文档相对较少，依赖团队纪律
- 需要用户高度参与
- 不适合需求完全固定或强合规的项目

### 使用时的角色分工
- Product Owner：定义价值、管理 Backlog
- Scrum Master：保障流程、消除阻碍
- 开发团队：跨职能自组织实现
- 用户：提供持续反馈

## 模式切换策略

软件工程允许在项目过程中**根据情况切换开发模式**。切换时执行以下动作：

### 触发切换的信号
- 需求从模糊变清晰 → 原型/敏捷 → 瀑布
- 需求开始频繁变化 → 瀑布 → 敏捷
- 项目风险显现 → 任何模式 → 螺旋（引入风险分析）
- 需要更早交付 → 瀑布 → 增量/敏捷

### 切换步骤
1. 评估当前项目状态（完成度、文档、风险）
2. 明确切换原因与目标
3. 保留已有产出物（文档、代码、测试）
4. 按新模式的工作流重新规划后续步骤
5. 通知团队与用户新的协作节奏

### 切换矩阵

| 从 \ 到 | 瀑布 | 原型 | 增量 | 螺旋 | 敏捷 |
|--------|------|------|------|------|------|
| 瀑布 | - | 需求不明时先做原型 | 拆分交付 | 风险高时转入 | 变化频繁时转入 |
| 原型 | 需求已明确后 | - | 分批实现 | 风险高时转入 | 转为正式迭代 |
| 增量 | 需求稳定后 | 增量需求不清时 | - | 风险高时转入 | 缩短周期转敏捷 |
| 螺旋 | 风险消除后 | 用原型降风险 | 低风险部分增量 | - | 风险低后转敏捷 |
| 敏捷 | 强合规需求时 | 用原型澄清故事 | 大功能分批 | 引入风险分析 | - |

## 模式与软件工程目标的对应

| 目标 | 最匹配模式 |
|------|-----------|
| 正确性 | 瀑布/螺旋（严格评审） |
| 可靠性 | 螺旋（风险分析） |
| 高效性 | 敏捷（持续优化） |
| 可维护性 | 增量/敏捷（模块化+重构） |
| 可重用性 | 所有（模块化设计） |
| 可扩展性 | 增量（整体架构） |
| 经济性 | 敏捷/增量（控制返工） |
