# 软件测试与维护详解

本文档详解软件测试的层次、类型、用例编写方法，以及软件维护的四类工作。供软件工程技能在执行测试与维护阶段时参考。

---

## 一、软件测试层次（V 模型对应）

测试从底向上，对应开发各阶段：

```
需求分析 ─────────────→ 验收测试
   │                       │
概要设计 ─────────────→ 系统测试
   │                       │
详细设计 ─────────────→ 集成测试
   │                       │
编码实现 ─────────────→ 单元测试
```

### 单元测试（Unit Test）
- **对象**：最小的代码单元（函数、方法、类）
- **执行者**：开发人员
- **工具**：JUnit、pytest、Jest、Go test 等
- **要点**：断言输入输出、覆盖分支边界

### 集成测试（Integration Test）
- **对象**：模块之间的协作与接口
- **策略**：
  - 自顶向下（需要桩 Stub）
  - 自底向上（需要驱动 Driver）
  - 大爆炸（全部一次性集成）
  - 持续集成（增量集成）
- **要点**：验证接口传递、数据一致性

### 系统测试（System Test）
- **对象**：整个系统
- **内容**：功能测试、性能测试、安全测试、兼容性测试、可靠性测试
- **要点**：从用户/系统整体视角验证非功能需求

### 验收测试（Acceptance Test）
- **对象**：用户视角的最终确认
- **类型**：Alpha（内部用户）、Beta（外部用户）
- **要点**：由用户确认是否满足需求（对照 SRS）

## 二、测试类型（按内部结构了解程度）

### 黑盒测试（Black-box Testing）
- 不关心内部实现，只看输入与输出
- **方法**：
  - 等价类划分：将输入域划分为等价类，每类取代表性数据
  - 边界值分析：测试输入边界（上点、内点、离点）
  - 决策表测试：组合条件与动作
  - 因果图、错误推测
- **适用**：功能测试、系统测试、验收测试

### 白盒测试（White-box Testing）
- 基于代码内部逻辑与执行路径
- **覆盖率标准**：
  - 语句覆盖：每条语句至少执行一次
  - 分支/判定覆盖：每个判定的真假分支都执行
  - 条件覆盖：每个条件的所有可能取值
  - 路径覆盖：所有路径
- **适用**：单元测试

### 灰盒测试（Gray-box Testing）
- 结合黑盒与白盒：了解部分内部结构，但从外部行为验证
- **适用**：集成测试、Web API 测试

## 三、测试用例模板

```markdown
### 测试用例 TC-001
- **用例ID**：TC-001
- **关联需求**：REQ-001
- **测试类型**：黑盒/白盒/灰盒
- **优先级**：高/中/低
- **前置条件**：
  - 系统已部署，用户已登录
- **输入数据**：
  - 字段A = ...
  - 字段B = ...
- **操作步骤**：
  1. ...
  2. ...
- **预期结果**：
  - ...
- **实际结果**：
  - （执行后填写）
- **状态**：通过/失败/阻塞
- **备注**：
```

## 四、测试计划内容（测试计划文档结构）

1. 测试目标与范围
2. 测试环境（硬件、软件、网络）
3. 测试策略与层次安排
4. 测试进度与资源
5. 测试用例设计说明
6. 缺陷管理与报告规范
7. 风险与应对
8. 验收标准（何时可发布）

---

## 五、测试报告内容（测试报告文档结构）

1. 测试概述（时间、人员、范围）
2. 测试执行情况（用例数、执行数、通过率）
3. 缺陷统计（按严重程度/模块分布）
4. 遗留问题与风险
5. 质量评估与发布建议

### 缺陷严重程度分级
- **致命（Blocker）**：系统崩溃、数据丢失
- **严重（Critical）**：核心功能不可用
- **一般（Major）**：功能有误但不阻塞
- **轻微（Minor）**：界面/文案小问题

## 六、软件维护四类详解

### 1. 纠错性维护（Corrective Maintenance）
- **目的**：修复已发现的软件缺陷（bug）
- **活动**：缺陷定位、修复、单元/回归测试
- **占比**：约占维护工作的 20%

### 2. 适应性维护（Adaptive Maintenance）
- **目的**：适应外部环境变化
- **触发**：操作系统升级、硬件更换、数据库版本、浏览器升级、业务环境/法规变化
- **活动**：移植、兼容性调整

### 3. 完善性维护（Perfective Maintenance）
- **目的**：优化性能、增加新功能、改善用户体验
- **活动**：功能增强、性能优化、界面改进
- **占比**：通常占维护工作的最大比例（约 50%）

### 4. 预防性维护（Preventive Maintenance）
- **目的**：改进软件内部结构，降低未来维护成本，防止缺陷发生
- **活动**：代码重构、文档更新、架构优化、增加可读性
- **理念**：面向未来，主动改善

### 维护阶段最佳实践
- 建立**缺陷跟踪系统**（Bug 记录、分级、指派）
- 定期**回归测试**防止修改引入新问题
- 维护**版本管理与变更记录**
- 维护代码与文档的同步更新
- 关注**技术债**，定期预防性维护

---

## 七、测试与维护的联动

| 场景 | 建议动作 |
|------|---------|
| 新增功能 | 补功能测试 + 回归测试 |
| 修复 bug | 先写复现用例 → 修复 → 回归 |
| 环境升级 | 适应性维护 + 兼容性测试 |
| 性能问题 | 性能测试 + 优化 + 回归 |
| 技术债累积 | 预防性重构 + 全量回归 |
